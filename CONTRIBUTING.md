# Contributing to WingHarness

Thanks for taking the time to contribute. This guide covers the development
setup, the conventions the project enforces, and the rules for carrying code
over from an upstream project.

By participating you agree to the [licensing terms](#licensing-of-contributions)
below and to keep discussion respectful and on topic.

## Before you start

- Search [existing issues](https://github.com/Anfioo/WingHarness/issues) before
  opening a new one.
- For anything larger than a bug fix or a small improvement, open an issue first
  so the approach can be agreed before you write code.
- Small, focused pull requests get reviewed faster than large ones.

`dev` is the working branch; `main` is the release branch. Open pull requests
against `dev`.

## Development setup

Prerequisites: Node.js >= 18, pnpm >= 9, Rust >= 1.70, plus the
[Tauri system dependencies](https://tauri.app/start/prerequisites/) for your OS.

```bash
pnpm install
pnpm tauri dev      # Vite on :11421 + the app
pnpm check          # prettier --check, eslint, tsc and vite build
```

`pnpm check` is the gate every pull request has to pass. Run it before pushing.

## Conventions

### Language

- **Comments, console logs and error strings must be in English.** This applies
  to both TypeScript and Rust.
- User-facing copy never lives in a component. It goes through i18next; see
  below.

### TypeScript / React

- TypeScript strict mode; function components with hooks.
- `@/` maps to `src/`.
- Format with Prettier (`pnpm format`). Do not reformat a file you did not
  otherwise change.
- Reach for the typed wrappers in `@/commands` instead of calling `invoke`
  directly.

### Rust

- Follow the Rust naming conventions.
- A Tauri command must be listed in four places — `src/invoke.rs`, `build.rs`,
  `capabilities/default.json` and `permissions/autogenerated/*.toml`.
  `src-tauri/CLAUDE.md` walks through it; `build.rs` fails the build when the
  first two disagree.

### Internationalization

English and Chinese must stay key-for-key identical, in
`src/i18n/locales/{en,zh}.json`. Do not add a key without a caller. See
[docs/I18N.md](docs/I18N.md).

### shadcn/ui

Add primitives with the CLI rather than hand-writing them:

```bash
pnpm dlx shadcn@latest add <component>
```

## Commits

Commit messages follow [Conventional Commits](https://www.conventionalcommits.org/).
`commitlint` and `husky` enforce the format on commit.

```
feat(preview): add Markdown rendering
fix(terminal): keep the cursor in view after resize
docs(contributing): describe the porting checklist
chore(deps): bump tauri to 2.12
```

Keep the subject in the imperative mood and under ~72 characters.

## Pull requests

Before opening one:

1. Rebase on the latest `dev`.
2. Run `pnpm check`.
3. If the change is user-visible, write the guide under `docs/features/` in
   **both** languages (`FEATURE.md` and `FEATURE.zh-CN.md`) and link it from both
   READMEs.
4. If the change carries code from an upstream project, update
   [THIRD_PARTY_NOTICES.md](THIRD_PARTY_NOTICES.md) and
   [docs/UPSTREAM_PROJECTS.md](docs/UPSTREAM_PROJECTS.md).

In the description, say **what changed and why**, and call out anything you
could not test (for example, a UI path you could not exercise).

## Porting code from an upstream project

WingHarness is GPL-3.0-only and ports features from other open-source projects
one at a time. Read [docs/UPSTREAM_PROJECTS.md](docs/UPSTREAM_PROJECTS.md)
before copying anything.

The short version:

- **Allowed:** GPL-3.0, MIT, BSD, ISC, Apache-2.0, MPL-2.0, LGPL.
- **Forbidden:** AGPL-3.0, and any project with no licence file. Default
  copyright is all rights reserved — ask the author first.
- Keep the attribution header in every ported file.
- Record the upstream version and what you changed, in the porting record or in
  a per-directory `UPSTREAM.md` for a whole subsystem.
- Do not copy from an intermediate copy without checking the **original**
  project's licence.

If you are unsure whether a licence is compatible, open an issue before writing
code.

## Reporting bugs

Include:

- WingHarness version (Settings → About) and your OS version;
- the steps that reproduce the problem;
- what you expected and what happened instead;
- relevant log output — the app's console or the terminal it was started from.

For a **security issue**, do not open a public issue. Use GitHub's private
vulnerability reporting on the repository's *Security* tab, or contact the
maintainer directly.
