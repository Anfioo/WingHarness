## §11 多子 Agent 开发方案

### 11.1 波次

| 波次 | 执行轨 | 波次结束协调 | 内容 | 开启下一波的条件 | 墙钟 |
|------|--------|--------------|------|------------------|------|
| W0 | A0（串行） | — | P0 基线 | A0 完成、接口冻结、门禁通过 | N |
| W1 | B1 / B2 / F1 | W1-C | <互斥内容> | W1-C 处理完待协调、门禁通过 | N |
| W2 | B3 / F2 | W2-C | <互斥内容> | W2-C 处理完待协调、门禁通过 | N |
| W3 | A1（串行） | — | 联调、补测、文档 | 最终门禁通过 | N |
| **合计** | | | | | **N** |

> 每波执行轨最多 3 个窗口；执行轨仍由用户按原提示词手动开启。每个施工波次结束后，必须先运行对应的 W*-C 协调者提示词，再开启下一波。

### 11.2 文件所有权（互斥）

| 轨 | 独占文件 |
|----|----------|
| A0/A1（执行与收尾） | `src-tauri/Cargo.toml`、`src-tauri/build.rs`、`src-tauri/capabilities/default.json`、`src-tauri/src/invoke.rs`、`src-tauri/src/lib.rs`、`src/main.tsx`、`src/lib/app-routes.ts`、`src/lib/sidebar-config.ts`、`src/commands/index.ts`、`src/commands/services/<domain>/*`、`src/pages/<module>/index.tsx`、`src/i18n/**`、`src-tauri/<module>-core/src/{lib,error,paths,models,commands}.rs`、`src-tauri/<module>-core/Cargo.toml` |
| W*-C（波次协调者） | 仅修改上表共享文件与协调记录；不得修改 B/F 轨独占业务文件，不负责派发 Agent |
| B1 | `src-tauri/<module>-core/src/<files>.rs`、`src-tauri/<module>-core/src/commands/<域>.rs` |
| B2 | … |
| F1 | `src/pages/<module>/<tab>.tsx`、`src/components/<module>/*` |
| F2 | … |
| 共享（只读） | 其余全部；要改就走本轨 inbox 的 `## 待协调` |

### 11.3 共享工作区协议

- 所有轨在**同一工作树、同一分支**工作；不建 worktree。
- 禁止 `git add -A` / `git add .`；只 add 自己独占的文件。
- 提交前 `git status`；出现非本轨改动不处理、不提交。
- 同一时间只跑一个 cargo 构建；不并发 `pnpm tauri dev`。
- 构建生成的 `permissions/autogenerated/*.toml`、`Cargo.toml` 的 CRLF-only 差异只按显式路径提交。
- 每波执行轨结束后，必须由对应的 W*-C 协调者读取并处理 `## 待协调`，通过门禁并报告下一波可开启，才能进入下一波。

```powershell
cd src-tauri
cargo check -p <module>-core
cargo test -p <module>-core
cd ..
pnpm build
pnpm exec eslint <本波新增文件>
```

### 11.4 派发顺序与波次协调

1. **A0**：基线。产出可编译空壳 + 命令桩 + 页面壳 + 事件契约 + 各轨 inbox；冻结 §6 的命令面与 DTO、§3 的公开签名。
2. 用户按提示词手动开启 **W1** 的 B1/B2/F1，只依赖 A0 桩。
3. W1 执行轨全部完成后，用户开启 **W1-C 波次收尾协调者**。它只读取并处理各轨「待协调」，更新允许的共享文件，跑门禁；未达到下一波前置条件时必须停止并报告。
4. 仅当 W1-C 明确报告工作区可以开启下一波后，用户才手动开启 **W2** 执行轨。
5. W2 执行轨全部完成后，开启 **W2-C 波次收尾协调者**，处理 W2 待协调并确认 A1 前置条件。
6. **A1**：用户在 W2-C 放行后开启，按 §8.3 验收清单逐项过，补测试与文档。

> W*-C 不派发执行 Agent、不替执行轨补业务逻辑、不静默跳过待协调；它的完成标志是当前工作区已达到可以开启下一波的程度。

### 11.5 提交消息规范（中文）

```
<type>(<scope>): <中文摘要，不超过 50 字>

- <要点一>
- <要点二>
```

- `type`：`feat` / `fix` / `docs` / `style` / `refactor` / `perf` / `test` / `build` / `ci` / `chore` / `revert`
- `scope`：`<module>`、`<module>-core`、<域>、`ui`、`i18n`
- 摘要 ≤ 100 字符（commitlint 上限），正文中文、每条以 `- ` 开头、与前文空一行。
- 代码注释、日志、错误消息仍为英文。

### 11.6 分支与工作树约束

1. 只有协调者在开工前从 `main` 创建并切换到 `feature/<module>`；之后任何轨不做分支操作。
2. 切换前 `git status --porcelain` 只允许出现本次任务自己的文件；有无关改动先停下问用户，**不得** stash/reset/clean。
3. 工作期间禁止 `checkout`/`switch`/`reset`/`clean`/`stash`/`rebase`/`merge`/`cherry-pick`/`pull`/`push`。
4. 需要更新基线时由协调者暂停所有轨，一次性处理。

### 11.7 提交点

| # | 提交消息 | 波次 |
|---|----------|------|
| 1 | `chore(<module>): 建立 <module>-core crate 与命令挂载骨架` | A0 |
| 2 | `feat(<module>): 增加侧边栏入口与页面空壳` | A0 |
| 3 | `feat(<module>-core): …` | B1 |
| … | … | … |
| N | `test(<module>-core): …` / `docs(<module>): …` / `fix(<module>): …` | A1 |

> 每个提交点单独提交，不积攒成总提交；`fix` 按实际修复项拆多条。
