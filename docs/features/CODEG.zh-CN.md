# Codeg

侧边栏的 **Codeg** 条目在本应用的标签页里打开一个页面，内容是第三方客户端
[Codeg](https://github.com/spacering-net/codeg)，以 **原生子 webview** 呈现——不是
`<iframe>`，也不是插件。Codeg 跟随本应用的外观和语言设置，因此它看起来是这个应用的
一个页面，而不是别人拥有的一扇窗口。

两条路由，一个页面组件，一个服务：

| 路由 | 模式 | 侧边栏条目 |
| --- | --- | --- |
| `/codeg` | **安装版**——应用从 Codeg 发布页下载的 `codeg-server` 归档 | 始终显示 |
| `/codeg-dev` | **开发版**——本机代码仓库构建出来的 `codeg-server` | 仅开发构建（`app-routes.ts` 里的 `devOnly`，由 `DEV_BUILD` 过滤） |

两者在同一端口上用不同目录启动同一个进程，所以访问另一种模式会先停掉、再重启。模式只
决定一次启动使用哪个可执行文件和哪份导出，以及该文件不存在时页面怎么说——页面其余部分
一模一样。

## 安装版归档

打包后的应用没有代码仓库，所以 Codeg 来自这个 fork 自己的发布页。每个版本都附带
`codeg-server-web-<tag>-windows-x64.zip`——可执行文件及旁边的 `web/` 导出——和一个固定
名字的 `server.json`，说明归档在哪里：

```json
{
  "version": "0.45.0",
  "tag": "wh.03.0.45.0",
  "platforms": {
    "windows-x86_64": { "url": "...", "sha256": "...", "size": 12345678 }
  }
}
```

`server.json` 的文件名里没有 tag，所以 `releases/latest/download/server.json` 永远能解析，
应用不必跟着版本号走。

两个端点，按顺序尝试（`codeg/install.rs`）：

| # | 端点 | 标签 |
| --- | --- | --- |
| 1 | `https://github.com/Anfioo/codeg/releases/latest/download/server.json` | GitHub |
| 2 | `https://wingharness.dpdns.org/WhCodeg/latest/server.json` | Cloudflare |

第二个是发布流程与 GitHub 并列发布的 R2 镜像：版本、tag、SHA-256 和大小完全一致，
只有归档地址指向镜像，因此任一端点装出来的字节都一样，GitHub 失败时会退到镜像而不是
让整次检查失败。`platforms` 的键沿用更新器的目标写法，也正是发布工作流写入的写法，因此
同一个查找函数既能读这份清单，也能读桌面更新器的那份。

归档解压在数据目录下，服务只从这里运行——设置里没有任何字段指向它们：

```text
<data dir>/codeg-server/
  codeg-server.exe
  web/            CODEG_STATIC_DIR
  install.json    version、tag、sha256、size、用了哪个镜像、何时安装
```

安装是四步，每一步落在进程的不同一侧：

1. **下载**走 moin 引擎（`src/lib/runtime/install.ts` 的 `downloadArchive`），因此传输
   直接获得应用的进度、续传和重试行为，临时任务随后被删除。
2. **校验**在后端（`codeg_install_read_archive`）：先比大小，再比清单里的 SHA-256，都在
   任何一个字节到达 webview 之前。截断的下载正是它存在的理由。
3. **解压**用 worker 里的 7z-wasm——和运行时安装器同一个 `extractArchive`。结果在动磁盘
   之前就检查过有没有 `codeg-server.exe` 和 `web/` 目录，所以拿错归档不付任何代价。
4. **写入**每个条目一条命令（`codeg_install_write_file`，裸请求体），最后由
   `codeg_install_finish` 记录装了什么。更新会先清空目录：新导出里已经删掉的文件若留在
   原处，照样会被服务出去。

安装或更新要求服务已停止——`codeg_install_clear` 否则拒绝执行，因为可执行文件和导出都在
被替换的目录里，而 Windows 根本不允许替换正在运行的映像。

更新是显式的，从不静默：设置分区按按钮才检查，清单版本比记录新时才提供下载。Codeg 页面
自己不做任何检查；没装就装，装了就直接启动。

## 一个 webview，多个页签

**每个宿主窗口自始至终只有一个 webview。** Codeg 自己的客户端会向浏览器要额外的窗口——
它的设置页就是一个——在本应用里这些绝不能变成第二份 Codeg。两处实现做到这点：

- 页面的 `window.open` 被初始化脚本替换。Codeg 先用 `window.open("", name)` 预留窗口，
  再给它赋路由；把页面本身交回去，就把那次赋值变成了原地导航，于是路由在唯一的 webview
  里改变。
- 前端每 400 ms 轮询一次 `codeg_browser_url`。路径变化变成一个应用页签栏里的页签——它就
  是 Codeg 那些窗口的替代品；点页签则在同一 webview 上调用 `codeg_browser_navigate`。

反方向——应用页签栏驱动 webview——由一个"请求中的路由" ref 守卫，使随后那次轮询看起来
不是新路由、不会自己多出一个页签。

因为页面是操作系统级别的视图，CSS 藏不住它：不是当前选中的页签，或者路由缓存了却不在屏
幕上的页面，都用 `codeg_browser_set_visible(false)` 隐藏。离开页面时 `pagehide` →
`codeg_browser_close_all` 关闭 webview，因为子 webview 属于窗口，否则会一直画在下一个
页面之上。

离开服务来源的链接由 `on_navigation` 拒绝并发出 `codeg-external-link`，页面把它交给系统
浏览器——这正是真实浏览器标签页里该发生的事。

## 服务

`codeg-server` 以五个环境变量启动——`CODEG_HOST=127.0.0.1`、`CODEG_PORT`、
`CODEG_TOKEN`、`CODEG_STATIC_DIR`、`CODEG_DATA_DIR`——工作目录是安装目录（开发模式下是
代码仓库），并且不弹控制台窗口。进程归应用所有：

- **启动**先校验配置：缺少 `codeg-server` 文件、缺少静态导出、端口已被别的程序占用，都在
  启动任何东西之前作为各自的提示报出。提示按模式区分——开发构建被告知去构建，安装版被告知
  去安装 Codeg。
- **就绪**是每 150 ms 轮询一次 `POST /api/get_system_language_settings`，最多 25 s，而不是
  固定睡眠：Codeg 启动时要加载一整套数据库客户端并扫描工作区，间隔无法预测。
- **停止**和**关闭**按 pid 结束整棵进程树。只用 `Child::kill` 会留下服务 daemon 化出去的
  子进程继续占着端口。
- 子进程的 stdout 和 stderr 被读进一个 200 行环形缓冲，由设置分区展示。
- 每一次状态变化都以 `codeg-status` 发出，载荷与 `codeg_state` 返回的一致，于是两个页面和
  两个设置分区都能跟上一次不是自己引起的启动、停止或崩溃。仍在显示内嵌页的页面会变成失败
  面板，而不是把一块死掉的面板留在最上层。

`RunEvent::Exit` 调用 `server::shutdown`，这就是退出应用会带走 `codeg-server` 的原因。

## 首帧

token 和外观由 `WebviewBuilder::initialization_script` 写入，它先于页面自己的任何脚本执行
——此时还没有 DOM，所以只碰 `localStorage` 和 `window`：

| 键 | 值 |
| --- | --- |
| `codeg_token` | 应用的 token，页面一启动就是已登录状态，从不显示登录表单 |
| `__CODEG_EMBEDDED__` | `true`；由 Codeg 的传输层开关读取（见 *Codeg 侧的改动*） |
| `theme` | `light` 或 `dark`，已由应用解析好 |
| `codeg-custom-theme` | 应用的调色板，形如 `{ light: {...}, dark: {...} }`，只含 Codeg 接受的 token |
| `codeg-theme-color` | `neutral` |
| `codeg-custom-theme-enabled` | `1` |
| `codeg-theme-preset` | 正在使用的预设 id；内置主题时为空 |
| `codeg-embed-theme-rev` | 下文所述的版本戳 |

这么早写入主题，正是首帧不会是 Codeg 默认亮色闪一下的原因。

`initialization_script` 是创建时刻的快照，而 WebView2 会在**每一次文档加载**时重跑它——
Codeg 自己的设置页就是一次，因为 `window.open` 的替换把它变成了原地导航。放任不管，它
就会用页面打开时的调色板覆盖应用此后应用过的东西，这正是版本戳要解决的"Codeg 设置页显示
旧主题"问题。每一次外观写入都带一个修订号——墙钟毫秒，跨重启严格递增——这个脚本只在它比
页面里已有的版本戳更新时才应用自己的快照。

## 外观

单向：应用的外观传给 Codeg，反方向从不。

- 页面用 `useTheme()` 和 `resolveMode(theme)` 取主题快照，用 `getComputedStyle` 取当前
  调色板（Codeg 白名单接受的 31 个语义 token 加 `radius`）；另一个桶来自
  `presetVars(preset, mode)`，这样 Codeg 自己的亮暗切换照常可用。任一时刻 Codeg 只用到与
  当前模式匹配的那个桶，而整个载荷在每次变化时重发。
- 预设 id 随载荷一起传。Codeg 内置同样这 42 套预设（`theme-preset-library.json`，id 与
  `src/lib/theme/presets.json` 完全一致），所以只要告诉它正在用哪一套，它的设置页就能把
  那张卡片标为已应用；内置主题发的是"没有预设"。id 只是标签，不是绘制指令——调色板依然是
  应用自己的值。
- 快照做 100 ms 防抖后交给 `codeg_browser_apply_theme`，它执行第二个脚本：写入
  `localStorage` 键，派发 `StorageEvent` 让 Codeg 自己的外观 provider 反应，并翻转
  `<html>` 的 `light`/`dark` 类和 `style.colorScheme`。整个过程不刷新，页面状态得以保留。
  每次运行都盖上 `codeg-embed-theme-rev`，这就是创建时快照在下次文档加载时退让的依据
  （见 *首帧*）。
- 字体、阴影和间距不跟随：它们不在 Codeg 的主题白名单里。
- Codeg 还在自己的数据库里存了一份外观——配置快照、还原或回滚会携带的那一行——由它自己的
  setter 写入。从外部注入的值不会写它，所以同一个脚本还会调用
  `POST /api/config_sync_mirror_appearance`，带着从页面读回的 Codeg
  `SYNCED_APPEARANCE_KEYS` 全部 28 个键：加载后 1.2 s 一次，重绘后 600 ms 再一次。写入是
  整体覆盖，所以整组键都从页面读，而不只是本应用改动的那几个。没有这一步，Codeg 的
  设置 → 外观会显示上一次的调色板，而一次快照会还原出应用从未应用过的颜色。
- 模式不在这批 `localStorage` 键里：Codeg 把它存在自己的设置中，它的原生窗口边框和启动
  流程都从那里读，而它的写入方是一个本内嵌无法触及的 `invoke`。因此镜像还会调用
  `POST /api/update_appearance_mode`，带着页面当前的模式，这就是独立启动 Codeg 时会以应用
  的亮色或暗色打开的原因。

## 语言

Codeg 把语言存在自己的数据库里，不在页面里，所以在页面打开之前通过
`POST /api/update_system_language_settings` 写入
`{"settings":{"mode":"manual","language":"zh_cn"|"en"}}`。页面只在启动时读一次该设置，
这就是应用里切语言会刷新当前页面的原因——一次刷新，这是有意允许的。写入是无条件的，是否
刷新由页面决定：被一次重渲染抢占的调用，其写入可能最后落地，所以"什么都没变"不是一个可以
据以决定不刷新的安全答案。

## 配置

全部在 `config.codeg` 里；路径或端口的改动在下次启动时生效，因此两个分区都在旁边放了重启
按钮。

| 设置项 | 默认值 | 说明 |
| --- | --- | --- |
| `port` | `3080` | 仅回环；端口被占用会报出，不会换端口重试。两种模式共用 |
| `dataDir` | 空 | 空表示 `<应用数据目录>/codeg`——与独立的 Codeg 默认使用同一个目录，所以内嵌页和单独打开的应用共用一个数据库 |
| token | — | 首次使用时生成并保存在数据目录（`codeg-token`）里，此后固定；可见、可复制 |

安装版归档不增加任何设置：它的两条路径跟着数据目录走，分区里只读展示，所以搬动数据目录就
把安装一起搬走了。*Codeg（开发）* 则增加代码仓库需要的三个路径：

| 设置项 | 默认值 | 说明 |
| --- | --- | --- |
| `repoPath` | `D:\codeg` | Codeg 的代码仓库；服务的工作目录 |
| `staticDir` | `D:\codeg\out` | `next build` 的导出，由服务提供 |
| `serverPath` | `D:\codeg\src-tauri\target\debug\codeg-server.exe` | 用 `cargo build --no-default-features --features server-bin --bin codeg-server` 构建 |

共用同一个默认数据目录是 Codeg 那侧的配合：它的桌面应用和 `codeg-server` 在没有预设
`CODEG_DATA_DIR` 时都解析到 `%APPDATA%\com.anfioo.wingharness\codeg`，也就是该目录下再加
一个 `codeg`，并且在本应用把数据目录搬到别处时跟着 `data-dir.txt` 走。只有一个数据库，
无论谁启动：内嵌页、单独运行的 Codeg，还是手工启动的服务。这里填写的 `dataDir` 只覆盖本
应用所启动的那个服务。

一次安装的两半必须来自同一次提交——服务配上另一份 `web/`，两边不一致的地方就是 404——
所以应用把它们作为一个归档整体更新，从不单独改动任一路径。

## 命令

共二十个，全部出现在四份清单里（`invoke.rs`、`build.rs`、`capabilities/default.json`、
`permissions/autogenerated/`）：

| 命令 | 作用 |
| --- | --- |
| `codeg_state` | 一次返回配置、安装版归档、服务状态、token 和日志 |
| `codeg_start`、`codeg_stop`、`codeg_restart` | 按模式启停服务并等它就绪；运行在另一模式的服务会先被停掉 |
| `codeg_set_language` | 写入 Codeg 自己的语言设置 |
| `codeg_release_check` | 读取已发布的 `server.json`——先 GitHub，再 Cloudflare——并告知已装版本 |
| `codeg_install_read_archive` | 按清单校验下载到的归档并把字节交回去 |
| `codeg_install_clear` | 清空安装目录，服务运行中拒绝执行 |
| `codeg_install_write_file` | 把解压出的一个条目写入安装目录 |
| `codeg_install_finish` | 记录一次完成的安装并返回新状态 |
| `codeg_browser_open` | 按占位组件的 bounds 打开页面，复用已有 webview |
| `codeg_browser_set_bounds`、`codeg_browser_set_visible` | 跟随占位组件，随页签隐藏 |
| `codeg_browser_navigate`、`codeg_browser_reload`、`codeg_browser_url` | 路由变化、刷新、地址轮询 |
| `codeg_browser_apply_theme` | 重绘已加载的页面 |
| `codeg_browser_devtools` | 打开开发者工具，仅开发构建 |
| `codeg_browser_close`、`codeg_browser_close_all` | 校验归属的关闭，在卸载和离开页面时调用 |

页面本身调不到这些命令：Tauri 会给每个 webview 注入 IPC 引导代码，但应用的 ACL 清单会
比对调用方来源，而由 `http://127.0.0.1:<port>` 提供的页面属于远程来源，不在任何 capability
覆盖范围内。页面做的一切都经过上面这些命令。

## Codeg 侧的改动

Codeg 是第三方代码仓库，内嵌本意是不动它；以下是例外，每一处都很小，且都是内嵌所需要的。

- `src/lib/transport/detect.ts` 增加 `isEmbeddedHost()` 判断——
  `window.__CODEG_EMBEDDED__ === true` 即"web"环境。Tauri 在它创建的每个 webview 上都会
  定义 `__TAURI_INTERNALS__`，子 webview 也不例外，所以没有这个标记，Codeg 会把自己当成
  自家的桌面应用并调用这里不存在的命令。有了它，三种形态都照常工作：内嵌在本应用里、
  普通浏览器、以及 Codeg 自己的桌面应用。
- 外观由两个客户端写入，所以 Codeg 需要一种在它自己窗口之外读写外观的方式：
  `codeg-theme-preset` 加入 `src/lib/appearance-sync.ts` 的同步键，以及它的
  `commands/config_sync/appearance.rs` 中的 `APPEARANCE_STORAGE_KEYS`；
  `POST /api/get_appearance_settings` 和 `POST /api/update_appearance_mode` 加入 web 路由，
  底层是 config-sync 域里的 `read_appearance_mirror` 和 `commands/appearance_mode.rs` 里的
  `set_mode`；桌面应用的启动步骤（`adoptOrMirrorAppearanceOnLaunch`）改为采纳已存的
  外观，而不是用自己的 `localStorage` 覆盖它。
- 它的设置页会记录并高亮正在使用的预设（`custom-style-section.tsx`，以及
  `appearance-provider.tsx` 里的 `activePreset` 状态）。
- `paths::wingharness_codeg_dir` 让共用数据目录成为它桌面应用和 `codeg-server` 的默认值，
  详见 *配置*。
- 发布工作流在它所描述的归档旁边发布 `server.json`，带 `sha256` 和 `size`，不带
  `signature`——归档未签名，空的签名字段只会诱使调用方去"验证"一个空值。

其余一切皆靠注入。如果将来的 Codeg 版本需要在它那侧再改什么，先说再动。

## 不在范围内

- 本应用的安装包里不附带任何静态导出或服务可执行文件：安装版归档在首次使用时从 Codeg
  发布页下载，页面只从回环地址提供。
- 没有 Codeg → 应用方向的同步：外观和语言都是单向的。
- 没有静默或定时的更新检查：更新发生在有人按下 设置 → Codeg 里的按钮时。
- 插件系统不受影响；这是一个独立模块。
