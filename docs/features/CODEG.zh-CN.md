# Codeg

侧栏的 **Codeg** 条目会在工作区打开一个页签，内容是用**原生子 webview**（不是
`<iframe>`，也不是插件）呈现的第三方客户端 [Codeg](https://github.com/spacering-net/codeg)。
访问从 Codeg 的对话首页（`/workspace`）开始；为它提供服务的 `codeg-server`
进程由应用自己启动和托管，所以新装之后不需要手动去启动任何东西。

仅开发模式。它是在这个壳里开发 Codeg 的入口，不是发布版本的功能：这里没有任何
东西会进入 release 包，应用也不分发任何静态导出产物。

## 文件

| 路径 | 职责 |
| --- | --- |
| `src-tauri/src/codeg/server.rs` | `codeg-server` 进程：配置检查、启动、输出环形缓冲、就绪轮询、退出监视、语言写入、状态与状态事件 |
| `src-tauri/src/codeg/webview.rs` | 子 webview：打开、位置尺寸、显示隐藏、导航、重载、地址轮询、主题重绘、外观镜像、源校验与注入脚本 |
| `src-tauri/src/commands/codeg.rs` | 十五个 `codeg_*` 命令；除 `codeg_state` 外都是 `async` + `spawn_blocking`，因为 Windows 上的 webview 调用必须在主线程 |
| `src-tauri/src/commands/mod.rs`、`invoke.rs`、`build.rs`、`capabilities/default.json`、`permissions/autogenerated/codeg_*.toml` | 四份手工维护的命令清单，以及生成的权限文件 |
| `src/pages/codeg/index.tsx` | 页面：服务启停、语言写入、Codeg 路由之上的页签栏、失败面板 |
| `src/components/codeg-browser.tsx` | 持有 webview 的占位区：自量尺寸、每个 host 只打开一次、跟随主题、上报页面路由 |
| `src/lib/codeg/theme.ts` | 把应用当前的调色板转成 Codeg 的 `codeg-custom-theme` 载荷 |
| `src/windows/settings/codeg-section.tsx` | 设置窗口的 **Codeg（开发）** 分区：路径、端口、数据目录、令牌、服务控制与日志 |
| `src/commands/services/codeg/` | 命令的类型化封装与 DTO，以及状态事件名 |
| `src/i18n/locales/codeg/` | `codeg.*` 的中英文文案 |

侧栏分组 `codeg` 故意不在 `src/lib/sidebar-config.ts` 的 `GROUP_ORDER`
中，因此条目落在**其他**。只有一个路由（`/codeg`），没有 `standalonePaths`
条目，也没有窗口记录。

## 一个 webview，多个页签

**每个宿主窗口永远只有一个 webview。** Codeg 自己的客户端会向浏览器要额外的窗口
（它自己的设置页就是），在本应用里这些不能变成第二份 Codeg。两处实现保证这一点：

- 初始注入脚本替换了页面的 `window.open`。Codeg 先用 `window.open("", name)`
  预留一个窗口，再把路由赋给它；把页面本身交回去，那次赋值就变成原地导航，路由
  因此始终改变的是同一个 webview。
- 前端每 400 ms 轮询一次 `codeg_browser_url`。路径变化就在应用的页签栏里多出一个
  页签——页签栏就是 Codeg 那些窗口的替代品；点页签则对同一个 webview 调用
  `codeg_browser_navigate`。

反方向（页签栏驱动 webview）用一个"已请求路由"的 ref 兜住，否则随之而来的轮询会
被当成新路由，再开出一个页签。

页面是系统级视图，CSS 藏不住它：不是当前选中页签、或被路由缓存但在屏幕外的页面，
都用 `codeg_browser_set_visible(false)` 显式隐藏。离开页面时通过 `pagehide` →
`codeg_browser_close_all` 关闭 webview，因为子 webview 属于窗口，否则它会一直盖在
下一个页面上面。

离开服务源的链接由 `on_navigation` 拒绝并以 `codeg-external-link` 抛出，页面把它
交给系统浏览器——也就是这个目标在真实浏览器标签页里会得到的结果。

## 服务

`codeg-server` 带五个环境变量启动——`CODEG_HOST=127.0.0.1`、`CODEG_PORT`、
`CODEG_TOKEN`、`CODEG_STATIC_DIR`、`CODEG_DATA_DIR`——工作目录是 Codeg 的源码
目录，不弹控制台窗口。进程由应用拥有：

- **启动**先校验配置：`codeg-server` 二进制不存在、静态导出不存在、端口已被占用，
  这三种都在真正启动进程之前给出各自的提示。
- **就绪**是每 150 ms 轮询一次 `POST /api/get_system_language_settings`，最多
  25 秒，而不是固定 sleep：Codeg 启动时要加载完整的数据库客户端并扫描工作区，
  时间不可预测。
- **停止**与**退出**都按 pid 杀进程树。只调 `Child::kill` 会留下服务自己
  daemon 化的进程继续占用端口。
- 子进程的 stdout 与 stderr 被抽进一个 200 行的环形缓冲，设置页显示它。
- 每次状态变化都以 `codeg-status` 事件抛出，载荷与 `codeg_state` 返回的一致，
  于是页面与设置窗口都能跟随一个不是它们自己发起启动、停止或崩溃。仍在显示嵌入页的
  页面会切换成失败面板，而不是留一块连到死服务的窗格。

`RunEvent::Exit` 调用 `server::shutdown`，这就是退出应用会带走 `codeg-server`
的原因。

## 首帧

令牌与外观由 `WebviewBuilder::initialization_script` 写入，它在页面自己的脚本之前
执行——此时还没有 DOM，所以它只碰 `localStorage` 与 `window`：

| 键 | 值 |
| --- | --- |
| `codeg_token` | 应用这一份的令牌，页面因此一上来就是登录态，不会闪登录表单 |
| `__CODEG_EMBEDDED__` | `true`；由 Codeg 的 transport 判断读取（见「Codeg 侧唯一的改动」） |
| `theme` | `light` 或 `dark`，由应用先行解析 |
| `codeg-custom-theme` | 应用调色板，形如 `{ light: {...}, dark: {...} }`，只含 Codeg 接受的令牌 |
| `codeg-theme-color` | `neutral` |
| `codeg-custom-theme-enabled` | `1` |

把主题写到这么早，首帧才不会闪一下 Codeg 默认的浅色主题。

## 外观

单向：应用的外观能传到 Codeg，反向不会。

- 页面用 `useTheme()` 与 `resolveMode(theme)` 取主题快照，用 `getComputedStyle`
  取当前调色板，范围就是 Codeg 白名单接受的那些令牌（31 个语义令牌加 `radius`）；
  另一个桶来自 `presetVars(preset, mode)`，好让 Codeg 自己的明暗切换继续可用。
  Codeg 在任一时刻只用与当前模式匹配的那个桶，而整个载荷在每次变化时整份重发。
- 快照做 100 ms 防抖后交给 `codeg_browser_apply_theme`，它执行第二个脚本：写入
  `localStorage` 的键、抛一个 `StorageEvent` 让 Codeg 自己的外观 provider 反应，
  并翻 `<html>` 的 `light`/`dark` 类与 `style.colorScheme`。全程不重载，页面的
  状态因此保留。
- 字体、阴影与间距不跟随：它们在 Codeg 的主题白名单之外。
- Codeg 自己的数据库里也存着一份外观副本——配置快照、恢复与回滚带走的就是它——
  由它自己的 setter 写入。从外部注入的值不会写这份副本，所以同一个脚本会调用
  `POST /api/config_sync_mirror_appearance`，带上从页面读回的 Codeg
  `SYNCED_APPEARANCE_KEYS` 全部 27 个键：加载后 1.2 s 一次，重绘后 600 ms 再一次。
  这个写入是整份替换，所以要从页面读回整个键集，而不是只发本应用碰的那几个。
  没有这一步，Codeg 的「设置 → 外观」会显示上一份调色板，快照恢复回来的也是应用
  从未应用过的外观。

## 语言

Codeg 的语言在它自己的数据库里，不在页面里，所以打开页面之前通过
`POST /api/update_system_language_settings` 写入
`{"settings":{"mode":"manual","language":"zh_cn"|"en"}}`。页面只在启动时读一次这个
设置，所以应用切换语言会重载已经打开的那个页面——一次重载，这是设计上允许的。
写入是无条件的，是否需要重载由页面判断：一个被重新渲染取代的调用，其写入可能才是
最后落地的，所以"没有变化"不是一个可以据以决定不重载的答案。

## 配置

全部在设置窗口的 **Codeg（开发）** 分区里，存在 `config.codeg`；改动在下次启动时
才到服务，所以分区里就放着重启按钮。

| 设置 | 默认值 | 说明 |
| --- | --- | --- |
| `repoPath` | `D:\codeg` | Codeg 源码目录，也是服务的工作目录 |
| `staticDir` | `D:\codeg\out` | 服务要托管的 `next build` 导出目录 |
| `serverPath` | `D:\codeg\src-tauri\target\debug\codeg-server.exe` | 用 `cargo build --no-default-features --features server-bin --bin codeg-server` 构建 |
| `port` | `3080` | 只监听回环；端口被占用会报错，不会自动换一个 |
| `dataDir` | 空 | 空表示 `<应用数据目录>/codeg`，这份副本因此永远不碰用户自己的 Codeg 数据库 |
| 令牌 | — | 首次使用时生成并落在数据目录（`codeg-token`），之后固定；界面可查看可复制 |

## 命令

十五个，全部写进四份清单（`invoke.rs`、`build.rs`、`capabilities/default.json`、
`permissions/autogenerated/`）：

| 命令 | 作用 |
| --- | --- |
| `codeg_state` | 一次返回配置、服务状态、令牌与日志 |
| `codeg_start`、`codeg_stop`、`codeg_restart` | 服务本身，并等到它应答 |
| `codeg_set_language` | 写入 Codeg 自己的语言设置 |
| `codeg_browser_open` | 按占位区的位置尺寸打开页面，已有 webview 则复用 |
| `codeg_browser_set_bounds`、`codeg_browser_set_visible` | 跟随占位区，随页签隐藏 |
| `codeg_browser_navigate`、`codeg_browser_reload`、`codeg_browser_url` | 路由切换、重载、地址轮询 |
| `codeg_browser_apply_theme` | 重绘一个已经加载好的页面 |
| `codeg_browser_devtools` | 打开 devtools，仅开发构建 |
| `codeg_browser_close`、`codeg_browser_close_all` | 带归属校验的关闭，用在卸载与离开页面时 |

页面本身调不到这些命令：Tauri 会给每个 webview 注入 IPC 引导脚本，但应用的 ACL
清单比对调用方源，而从 `http://127.0.0.1:<port>` 提供的页面是远程源，没有任何
capability 覆盖它。页面的一切动作都走上面这些命令。

## Codeg 侧唯一的改动

`D:\codeg\src\lib\transport\detect.ts` 增加了一个 `isEmbeddedHost()` 判断——
`window.__CODEG_EMBEDDED__ === true` 表示 "web" 环境。Tauri 会给它创建的每个
webview（包括子 webview）定义 `__TAURI_INTERNALS__`，没有这个标记，Codeg 会把
自己当成自家桌面应用，去调用这里并不存在的命令。有了它，三种模式都照常工作：
嵌在本应用里、普通浏览器、Codeg 自己的桌面应用。

其余全靠注入。如果将来的 Codeg 版本在它那侧还需要别的改动，先说明再改。

## 不在范围内

- 打包：不随包发布静态导出或服务二进制，页面也只在回环上托管。
- 没有 Codeg → 应用的同步：外观与语言都是单向的。
- 插件系统不动；这是独立模块。
