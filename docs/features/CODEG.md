# Codeg

The **Codeg** entry opens a tab in the app workspace whose content is the
third-party [Codeg](https://github.com/spacering-net/codeg) client, shown as a
**native child webview** — not an `<iframe>`, not a plugin. Codeg's chat home
(`/workspace`) is where a visit starts; the server that serves it is started and
owned by the app, so nothing has to be started by hand after a fresh install.

Development only. This is a way to work on Codeg from inside the shell, not a
feature of the shipped bundle: nothing here is packaged into a release and no
static export is redistributed with the app.

## Files

| Path | Responsibility |
| --- | --- |

| `src-tauri/src/codeg/webview.rs` | The child webview: open, bounds, show/hide, navigate, reload, address poll, theme repaint, the appearance mirror, the origin guard and the injection scripts |
| `src-tauri/src/commands/codeg.rs` | The fifteen `codeg_*` commands; everything but `codeg_state` is `async` + `spawn_blocking` because Windows webview calls must run on the main thread |
| `src-tauri/src/commands/mod.rs`, `invoke.rs`, `build.rs`, `capabilities/default.json`, `permissions/autogenerated/codeg_*.toml` | The four hand-maintained command lists, plus the generated permissions |
| `src/pages/codeg/index.tsx` | The page: server start/stop, language write, the tab bar over Codeg's routes, the failure panel |
| `src/components/codeg-browser.tsx` | The placeholder that owns the webview: measures itself, opens once per host, follows the theme, reports the page's route |
| `src/lib/codeg/theme.ts` | Turns the app's live palette into Codeg's `codeg-custom-theme` payload |
| `src/windows/settings/codeg-section.tsx` | The Settings window's **Codeg (dev)** section: paths, port, data directory, token, server controls, log |
| `src/commands/services/codeg/` | Typed wrappers over the commands and their DTOs, and the status event name |
| `src/i18n/locales/codeg/` | The `codeg.*` strings, English and Chinese |

Sidebar group `codeg` is deliberately absent from `GROUP_ORDER` in
`src/lib/sidebar-config.ts`, so the entry lands in **其他** (Other). There is one
route (`/codeg`), no `standalonePaths` entry and no window record.

## One webview, many tabs

**One webview per host window, ever.** Codeg's own client asks the browser for
extra windows — its settings page is one — and in this app those must not become
a second copy of Codeg. Two pieces make that work:

- The page's `window.open` is replaced by the initialisation script. Codeg
  reserves a window with `window.open("", name)` and then assigns the route to
  it; handing back the page itself turns that assignment into an in-place
  navigation, so the route changes in the single webview.
- The frontend polls `codeg_browser_url` every 400 ms. A changed path becomes a
  tab in the app's tab bar, which is what stands in for Codeg's windows; clicking
  a tab calls `codeg_browser_navigate` on that same webview.

The reverse direction — the app's tab bar moving the webview — is guarded by a
"requested route" ref so the poll that follows does not look like a new route and
add a tab of its own.

Because the page is an OS-level view, CSS cannot hide it: a tab that is not the
selected one, or a page the router keeps cached but off screen, is hidden with
`codeg_browser_set_visible(false)`. Leaving the page closes the webview through
`pagehide` → `codeg_browser_close_all`, since a child webview belongs to the
window and would otherwise stay painted over the next page.

Links that leave the server's origin are refused by `on_navigation` and emitted as
`codeg-external-link`, which the page hands to the system browser — what the
target would have done in a real browser tab.

## The server

`codeg-server` is spawned with five environment variables —
`CODEG_HOST=127.0.0.1`, `CODEG_PORT`, `CODEG_TOKEN`, `CODEG_STATIC_DIR`,
`CODEG_DATA_DIR` — with Codeg's checkout as the working directory, and no console
window. The app owns the process:

- **Start** validates the configuration first: a missing `codeg-server` binary,
  a missing static export, and a port something else already holds are all
  reported as their own message before anything is spawned.
- **Readiness** is a poll of `POST /api/get_system_language_settings` every
  150 ms for 25 s, not a fixed sleep: Codeg loads a full database client and
  scans the workspace at boot, so the interval is not predictable.
- **Stop** and **shutdown** kill the process tree by pid. `Child::kill` alone
  would leave whatever the server daemonised free to keep the port.
- The child's stdout and stderr are drained into a 200-line ring buffer the
  settings section shows.
- Every state move is emitted as `codeg-status` with the same payload
  `codeg_state` returns, so the page and the settings window both follow a start,
  a stop or a crash that neither of them caused. A page still showing the embed
  turns into the failure panel instead of leaving a dead pane on top.

`RunEvent::Exit` calls `server::shutdown`, which is what makes quitting the app
take `codeg-server` with it.

## First frame

The token and the appearance are written from
`WebviewBuilder::initialization_script`, which runs before any of the page's own
scripts — there is no DOM yet, so it touches only `localStorage` and `window`:

| Key | Value |
| --- | --- |
| `codeg_token` | The app's token, so the page starts signed in and never shows its login form |
| `__CODEG_EMBEDDED__` | `true`; read by Codeg's transport switch (see *The one Codeg-side change*) |
| `theme` | `light` or `dark`, already resolved by the app |
| `codeg-custom-theme` | The app's palette as `{ light: {...}, dark: {...} }`, limited to the tokens Codeg accepts |
| `codeg-theme-color` | `neutral` |
| `codeg-custom-theme-enabled` | `1` |

Writing the theme this early is what keeps the first frame from being a flash of
Codeg's default light theme.

## Appearance

One-way: the app's appearance reaches Codeg, never the other way round.

- The page takes a snapshot of the theme with `useTheme()` and
  `resolveMode(theme)`, and of the live palette with `getComputedStyle` over the
  tokens Codeg's whitelist accepts (31 semantic tokens plus `radius`); the other
  bucket comes from `presetVars(preset, mode)` so Codeg's own light/dark switch
  keeps working. Only the bucket matching the current mode is used by Codeg at
  any moment, and the whole payload is re-sent on every change.
- The snapshot is debounced by 100 ms and handed to
  `codeg_browser_apply_theme`, which runs a second script: it writes the
  `localStorage` keys, dispatches a `StorageEvent` so Codeg's own appearance
  provider reacts, and flips `<html>`'s `light`/`dark` class and
  `style.colorScheme`. No reload is involved, so the page keeps its state.
- Fonts, shadows and spacing are not followed: they are outside Codeg's theme
  whitelist.
- Codeg also keeps a copy of its appearance in its own database — the row a
  config snapshot, restore or rollback carries — and its own setters write that
  copy. A value injected from outside does not, so the same script calls
  `POST /api/config_sync_mirror_appearance` with all 27 keys of Codeg's
  `SYNCED_APPEARANCE_KEYS`, read back from the page: once 1.2 s after load, and
  again 600 ms after a repaint. The write is wholesale, which is why the whole
  set is read from the page rather than only the keys this app touches. Without
  this, Codeg's Settings → Appearance would show the previous palette and a
  snapshot would restore one the app never applied.

## Language

Codeg keeps its language in its own database, not in the page, so it is written
through `POST /api/update_system_language_settings` with
`{"settings":{"mode":"manual","language":"zh_cn"|"en"}}` before the page is
opened. The page reads that setting once, at boot, which is why a language change
in the app reloads whatever page is open — one reload, allowed for by design. The
write is unconditional and the reload is decided by the page: the write of a
call that a re-render superseded can be the one that lands last, so "nothing
changed" is not a safe answer to reload on.

## Configuration

All of it lives in the Settings window's **Codeg (dev)** section, in
`config.codeg`; changes reach the server on the next start, so the section keeps a
restart button next to them.

| Setting | Default | Notes |
| --- | --- | --- |
| `repoPath` | `D:\codeg` | Codeg's checkout; the server's working directory |
| `staticDir` | `D:\codeg\out` | The `next build` export the server serves |
| `serverPath` | `D:\codeg\src-tauri\target\debug\codeg-server.exe` | Build with `cargo build --no-default-features --features server-bin --bin codeg-server` |
| `port` | `3080` | Loopback only; a port in use is reported, not retried elsewhere |
| `dataDir` | empty | Empty means `<app data dir>/codeg`, so this copy never touches the user's own Codeg database |
| token | — | Generated on first use and persisted in the data directory (`codeg-token`), then fixed; shown and copyable |

## Commands

Fifteen, all named in the four lists (`invoke.rs`, `build.rs`,
`capabilities/default.json`, `permissions/autogenerated/`):

| Command | Does |
| --- | --- |
| `codeg_state` | Configuration, server status, token and log in one view |
| `codeg_start`, `codeg_stop`, `codeg_restart` | The server, waiting for it to answer |
| `codeg_set_language` | Writes Codeg's own language setting |
| `codeg_browser_open` | Opens the page over the placeholder's bounds, reusing the webview |
| `codeg_browser_set_bounds`, `codeg_browser_set_visible` | Follow the placeholder, hide with the tab |
| `codeg_browser_navigate`, `codeg_browser_reload`, `codeg_browser_url` | Route changes, reload, the address poll |
| `codeg_browser_apply_theme` | Repaints an already-loaded page |
| `codeg_browser_devtools` | Opens the devtools, in development builds only |
| `codeg_browser_close`, `codeg_browser_close_all` | Ownership-checked close, on unmount and on page leave |

The page itself cannot call these: Tauri injects its IPC bootstrap into every
webview, but the app's ACL manifest compares the caller's origin, and a page
served from `http://127.0.0.1:<port>` is a remote origin that no capability
covers. Everything the page does goes through the commands above.

## The one Codeg-side change

`D:\codeg\src\lib\transport\detect.ts` gets an `isEmbeddedHost()` check —
`window.__CODEG_EMBEDDED__ === true` means the "web" environment. Tauri defines
`__TAURI_INTERNALS__` on every webview it creates, child webviews included, so
without this marker Codeg takes itself for its own native desktop app and calls
commands that do not exist here. With it, all three modes keep working: embedded
in this app, a plain browser, and Codeg's own desktop app.

Everything else is injection. If a future Codeg release needs another change on
its side, say so before making it.

## Not in scope

- Packaging: no static export or server binary is shipped, and the page is not
  hosted anywhere but loopback.
- No Codeg → app sync: appearance and language are one-way.
- The plugin system is untouched; this is its own module.
