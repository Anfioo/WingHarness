# WingHarness — browser download capture

A companion extension that hands your browser's downloads to [WingHarness](../).
It uses the browser's resolved download request, so redirect and login flows can
finish before WingHarness receives the file URL:

- **Browser download capture** — the browser follows redirects and creates its
  download entry. The extension waits for the final URL and the first file bytes,
  then pauses the browser copy and submits that resolved URL to WingHarness. This avoids mistaking a landing
  page or an authentication endpoint for the actual file.
- **Response interception, Firefox only** — Firefox can cancel a
  `Content-Disposition: attachment` response before the browser's save dialog and
  hand its final response URL to WingHarness.

On Chrome, the browser may show its save dialog before the extension sees the
resolved download. Disable Chrome's **Ask where to save each file before
downloading** setting if you do not want that dialog. A direct **Download with
WingHarness** context-menu action also lets the browser resolve the request
first, then hands the resolved download over.

All paths include cookies, referer, and user-agent, so logged-in / gated
downloads work. You can also always right-click a link/image/video →
**Download with WingHarness**.

**Auto-capture is off by default.** Out of the box the extension only acts when
you explicitly choose **Download with WingHarness** from the context menu. When
you enable auto-capture in the options page, ordinary browser downloads are
handed over after the browser resolves their final URL.

If WingHarness isn't running when you capture something, the extension says so and
asks you to start it. **It cannot start the app for you** — there is no custom URL
scheme and no deep link — so the prompt offers to wait: start WingHarness from your
Start menu / launcher, click **I started it**, and the download is queued. Decline
and the browser downloads it normally.

## Setup

1. **Start WingHarness.** In **Settings → Browser integration**, turn it on, copy
   the **access token**, and note the port (default `47653`). This is the only
   place the token comes from — it's generated by the app and stored in its
   `settings.json`; the extension never invents one.
2. Load the extension (below).
3. Open the extension's **options** (click the toolbar icon), paste the token, set
   the port if you changed it in the app, and click **Test connection** — it should
   say "Connected to WingHarness ✓".

Port and token must match on both sides. Changing the port or the on/off switch in
WingHarness takes effect after restarting the app; a regenerated token takes effect
immediately, but you must paste the new one into the extension's options too.

## Load it (development)

The extension is plain JavaScript — there is no compile step. Load the `extension/`
folder itself.

### Chrome / Edge / Brave

1. Go to `chrome://extensions` (or `edge://extensions`, `brave://extensions`).
2. Turn on **Developer mode**.
3. **Load unpacked** → select this `extension/` folder.

### Firefox

Firefox needs its own manifest (background scripts instead of a service worker), so
build the per-browser folders first:

```
node build.mjs
```

Then in `about:debugging#/runtime/this-firefox` → **Load Temporary Add-on…** → pick
`dist/firefox/manifest.json`.

> Firefox may ask you to grant host access the first time it reads cookies or
> reaches WingHarness — allow it. Temporary add-ons are removed when Firefox
> restarts, so re-load it after a restart.

`node build.mjs` also writes zips to `dist/` (`wingharness-chrome-<version>.zip`,
`wingharness-firefox-<version>.zip`) for handing a build to someone else. That is
all the build does — it never touches the app's `pnpm build`.

## How it talks to WingHarness

Everything goes over WingHarness's **loopback-only** RPC
(`http://127.0.0.1:<port>`), authenticated with the access token. No request ever
leaves your machine.

- `GET /ping` → `{ "app": "wingharness", "version": "…" }`, no auth. Used to check
  the app is up.
- `POST /add` with `Authorization: Bearer <token>` and
  `{ "url": "...", "headers": { "Cookie": "...", "Referer": "...", "User-Agent": "..." }, "filename": "..." }`.
  Returns the created task, or a non-2xx with `{ "error": "..." }`.

The "Test connection" button posts an empty body to `/add`: `401` means the token
is wrong, `400` ("no URL") means the token is right and the app is reachable.

## Troubleshooting

**"WingHarness isn't running" / "Couldn't reach WingHarness".**
The app isn't up, or the port doesn't match. Start WingHarness, check
**Settings → Browser integration** is enabled, and confirm the port there equals the
one in the extension's options (default `47653`). Browser integration only binds
once at startup — if you just changed the port or enabled it, restart the app.

**"Reached WingHarness, but the token is wrong" (401).**
The token in the options page is stale. Copy the current token from
**Settings → Browser integration** and paste it again — the app reads the token on
every request, so no restart is needed. If you regenerated it, the old one stops
working everywhere.

**The port is already in use.**
WingHarness logs a warning and keeps running without browser integration (it never
crashes over it). Pick another port in **Settings → Browser integration**, restart
the app, then put the same port in the extension's options. Only one process can
hold the port.

**Downloads still open the browser's save dialog.**
Auto-capture is off by default — enable **Auto-capture downloads** in the options.
Chromium only exposes the download to the extension after the browser has resolved
its redirects, so the dialog may appear first. Turn off Chrome's "Ask where to save
each file before downloading" to suppress it.

**WingHarness receives an HTML page instead of the file.**
Reload the extension from the browser's extensions page so the updated version is
active. The content script no longer intercepts a link based only on its filename;
with auto-capture enabled, let the browser follow the link and redirects. The
extension waits for the browser's final download URL before handing it off. If
using the context menu, choose the download action on the link and let the browser
resolve it first.

**Right-click does nothing.**
Check the **Enable WingHarness capture** switch, and that the link is a direct
`http(s)` URL. Streaming media, `blob:` and `data:` URLs can't be handed off —
WingHarness can't re-fetch something that only exists inside the browser — so those
always stay with the browser.

**Nothing arrives in WingHarness.**
Look at the app's download list first (the notification fires when `/add` returns
2xx), then at the app's log for the RPC request. The extension logs to the
background console with a `[wingharness]` prefix: `chrome://extensions` →
**Inspect views: service worker** (Firefox: `about:debugging` → **Inspect**).

## Privacy

See [PRIVACY.md](./PRIVACY.md). Everything the extension collects — the download
URL, the browser's filename, that URL's cookies, the referer and the user-agent —
goes to `127.0.0.1` and nowhere else.

## Layout

```
extension/
  manifest.json            Chrome/Edge/Brave (MV3, service worker)
  manifest.firefox.json    Firefox (MV3, background scripts)
  build.mjs                assembles dist/chrome and dist/firefox, then zips them
  icons/                   WingHarness icon (SVG source + 32/48/128 PNG)
  src/
    shared.js              config + WingHarness API (ping / verify / send), cookie header
    content.js             in-page "start WingHarness" prompt
    background.js          context menu, response/download capture and retry prompt
    prompt.html/.js        fallback popup-window prompt (restricted pages)
    options.html/.js/.css  pairing (port + token) and capture toggles
```

Clicking the toolbar icon opens these options. The "start WingHarness" prompt
appears in-page over the current tab; on a page that can't host it (a freshly
opened tab before the content script loads, or a browser page like the extension
store) it falls back to a small popup window.
